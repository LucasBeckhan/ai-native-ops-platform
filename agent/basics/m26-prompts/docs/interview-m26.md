> 每道题：**面试官在考察什么** → **标准答案** → **加分回答** → **常见误区**

## Q1. 用非技术人员能听懂的方式解释 Transformer 的核心机制，以及它为什么能"理解"上下文

**面试官在考察什么**：技术表达与抽象能力——能把注意力机制讲给产品经理听的人，才能写好技术方案。同时验证你是否真懂而非背名词。

**标准答案**：LLM 的本质是"给定前文预测下一个 Token 的概率分布"。Transformer 的核心是**自注意力**：处理每个词时，计算它与句中所有词的相关度权重，按权重加权汇总信息——所以"它"这个代词能"看到"几句话前的"基站 eNB-1024"。位置编码注入语序信息；多层堆叠让浅层学语法、深层学语义；海量的"预测下一个词"训练让这种机制涌现出推理能力。

**加分回答**：① 用运维例子讲注意力："88°C 这个读数会与'温度传感器''eNB-1024'强关联，与'光模块'弱关联——这就是注意力权重"；② 指出上下文窗口的物理来源（位置编码数量）与工程含义（窗口内信息才是模型知道的，外部知识必须靠 RAG 注入——为模块 30 埋线）；③ 提到 KV Cache：生成时已算过的 Key/Value 不重算，这是推理加速的基石（模块 34 呼应）。

**常见误区**：堆砌名词（多头/QKV/位置编码）没有一句人话解释；说"LLM 理解了世界"（它是条件概率生成器，幻觉的根源也在此）；不知道 Token 不是"词"。

## Q2. Temperature 和 TopP 分别控制什么？生产中怎么选？

**面试官在考察什么**：是否理解"LLM 输出的是分布而不是确定值"这一根本机制，以及参数选择是否有工程依据。

**标准答案**：模型输出下一 Token 的概率分布。Temperature 对 logits 缩放（T→0 分布尖锐化=贪心，T>1 拉平=发散）；TopP（核采样）只在累积概率达 P 的候选集中采样，动态截断长尾。生产选型：结构化抽取/分类 T=0~0.2（稳定可解析）；推理分析 T=0.2~0.5；创意生成 T=0.5~0.7；回归测试 T=0。两者二选一调节即可。

**加分回答**：① 指出"参数只在采样阶段起作用，模型能力不变"——调参不能把 40% 准确率的任务调成 90%；② Seed 参数：部分厂商支持固定 seed 复现输出，测试环境比 T=0 更强的确定性工具；③ 指出 JSON mode/结构化输出约束（如 OpenAI structured outputs）优先级高于调温度——用机制保证而不是概率倾向。

**常见误区**：认为调高温度能"提升创造力质量"（只会更随机）；同时大幅调 T 和 TopP；不知道 T=0 也可能有非确定性（浮点并行归约顺序）。

## Q3. 设计"网络告警根因定位"的 Prompt，你的完整思路是什么？

**面试官在考察什么**：Prompt 工程的系统方法论——是否有一套结构（角色/上下文/任务/格式/兜底），是否理解领域特性（多假设）。

**标准答案**（五段式 + 领域设计，见本项目 prompt_templates.py ROOT_CAUSE 模板）：① 角色：资深网络故障诊断专家 + "禁止编造"的硬约束；② 上下文：告警 JSON + 近期变更单 + 知识库相似案例（数据优于描述）；③ 任务：归纳时空分布特征 → 列 2~3 个假设 → 逐个评估证据 → 给出 top_cause + confidence；④ 格式：严格 JSON（hypotheses/top_cause/confidence/next_steps）；⑤ 兜底：证据不足时 confidence<0.5 并给 next_steps 要求补数据——反幻觉的最便宜手段。

**加分回答**：① 强调"多假设"是网络故障的领域本质（硬件/配置/容量/施工/软件五类因），单假设 Prompt 会产生过早收敛的伪答案；② Few-shot 示例必须覆盖"变更加根因"和"非变更加根因"两类边界；③ 指出变更单是网络故障最高频关联因子，Prompt 里它的位置和权重设计直接影响输出质量；④ 评估闭环：模板改动必须跑标注回归集（20~50 条）。

**常见误区**：一上来就问"根因是什么"（无过程引导）；上下文塞满无关历史告警（Token 浪费+噪声）；输出不约束 JSON（下游无法编程）。

## Q4. CoT（思维链）为什么有效？什么时候不该用？

**面试官在考察什么**：对 Prompt 技巧背后机制的把握，以及成本意识——面试官想看你是否理解 CoT 的代价。

**标准答案**：CoT 把中间推理步骤显式写入上下文。原理：自回归模型每一步生成以前文为条件——写出"步骤 1：影响面是 200 用户"之后，下一步预测就站在更完整的信息之上，等价于给模型"打草稿"。不该用的场景：简单分类/抽取（直接答案即可，CoT 反而增加延迟与成本）、高并发低价值任务、以及输出 Token 计费敏感的管道。

**加分回答**：① 给出量化直觉：CoT 输出 Token 常常 3~10 倍于直接回答，延迟同比例上升；② 进阶：CoT 的"推理正确率不保证"——错误的中间步骤会自我强化，工程上配合 self-consistency（多次采样投票，成本再乘 N）；③ 通信场景取舍：告警分级不上 CoT，根因分析上 CoT+多假设，修复建议上 CoT 但步骤数限制在 5 步内。

**常见误区**：把 CoT 当万能增益；不知道 zero-shot CoT（"让我们一步步思考"）与 few-shot CoT 的区别；忽略成本。

## Q5. LLM 幻觉在运维场景有什么特殊危害？你在 Prompt 层和系统层各有什么防御手段？

**面试官在考察什么**：安全与可靠性意识——运维场景的幻觉会直接变成错误操作，这是 Agent 上生产的最大门槛。

**标准答案**：运维危害：编造不存在的设备/端口/命令 → 自动执行时制造真实故障；编造根因 → 误导处置延误恢复。Prompt 层防御：① 硬约束"只依据提供的数据，不编造"；② 兜底出口（NEED_MORE_INFO / confidence 阈值）；③ 严格 JSON + 枚举封闭（severity 只能取三个值）；④ 让模型引用证据（"每个结论标注来源告警 ID"）。系统层防御：工具返回的数据做事实校验（模块 31）、关键操作二次确认（模块 29 权限沙箱）、RAG 检索质量保证（模块 30）、输出护栏（模块 33）。

**加分回答**：① 举出通信场景具体例子：LLM 幻觉出一条 `reset-board eNB-1024 slot-3` 命令而该设备没有 slot-3——所以命令执行类工具必须白名单+参数校验；② 指出"幻觉率与任务自由度正相关"：抽取类幻觉率最低、开放推理最高，所以管道设计要"窄化自由度"；③ 提到 RAG 场景的归因幻觉（引用了不存在的来源），需要评估框架持续监控（RAGAS）。

**常见误区**：只答"加一句不要编造"（单层防御）；不了解系统层手段；认为 temperature=0 能消除幻觉（确定性与正确性是两回事）。

## Q6. Prompt 应该作为"资产"如何管理？给出你的工程化方案

**面试官在考察什么**：从调 Prompt 到管理 Prompt 的工程成熟度——高级岗的核心区分点。

**标准答案**：① **版本化**：模板入 Git，带版本号与变更说明，评审合入；② **变量化**：统一渲染器（缺失变量显式报错，见本项目 PromptTemplate），杜绝散落的字符串拼接；③ **评估集**：每类任务 20~50 条标注样本，模板改动跑回归对比（准确率/格式合规率/Token 成本三项）；④ **灰度发布**：新旧模板按流量比例分流，指标回看后全量；⑤ **可观测**：每次调用记录模板版本号，线上问题可归因到具体版本。

**加分回答**：① 提到 Prompt 与代码的解耦：模板文件独立目录、支持热更新（模块 34 Harness 生产化），业务迭代不用发版；② A/B 框架：按用户/流量维度分流并统计业务指标（告警分析采纳率）；③ 指出与"多模型路由"的联动：同一模板在不同模型上的表现不同，评估集要按模型分别维护（模块 27 的路由设计）。

**常见误区**：把 Prompt 硬编码在业务代码里；没有回归评估就上线新模板；无版本归因导致线上问题无法定位是哪版模板的问题。
