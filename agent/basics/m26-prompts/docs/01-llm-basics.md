## 1. 从直觉理解 Transformer：LLM 到底在做什么

把大语言模型抽象成一句话：**给定前文，预测下一个 Token 的概率分布**。所有"智能"都来自把这一步做到极致。

### 1.1 三个核心概念的最小解释

**Token（词元）**：模型处理的文本单位，不是"字"也不是"词"，是 BPE（Byte Pair Encoding）算法从语料中统计出来的高频子串。中文通常 1 字 ≈ 1~2 Token，英文 1 词 ≈ 1.3 Token。**上下文窗口按 Token 计费、按 Token 截断**——所以运维 Prompt 里塞 10 份完整告警不如塞 3 份关键告警。

**注意力（Attention）**：对输入序列的每个 Token，模型计算它与**所有**其他 Token 的相关度权重，按权重加权汇总信息。效果上实现了"代词回指""长距离依赖"：句子"它和上一条告警同源"里，"它"的注意力会聚焦到"上一条告警"。

**位置编码（Positional Encoding）**：注意力本身对顺序无感（集合运算），需要给每个 Token 注入位置信息模型才知道语序。这也是"上下文窗口"的物理来源——位置编码的数量决定了能同时处理的长度。

```
输入:  "基站   eNB-1024   的   温度   传感器   读数   88°C"
        ▲       ▲              ▲
        └───────┴── 注意力权重把 "88°C" 与 "温度" "eNB-1024" 强关联
        
输出概率分布（示意）:
  已超阈值: 62%   正常波动: 21%   需要人工: 9%   其他: 8%
        → 采样得到下一个 Token
```

### 1.2 Temperature 与 TopP：采样参数的工程含义

模型输出的是概率分布，"生成"是从分布中**采样**：

- **Temperature（温度）**：对分布做缩放。`T→0` 分布尖锐化，几乎总选最高概率（确定性最强，适合**结构化抽取/分类**）；`T→1` 原始分布（均衡）；`T>1` 拉平分布（发散，适合**头脑风暴**）。
- **TopP（核采样）**：只在累积概率前 P 的候选里采样。TopP=0.9 表示"只考虑占 90% 概率质量的词"，动态截断长尾。

**工程决策表**（面试可直接引用）：

| 场景 | 推荐 | 原因 |
|---|---|---|
| 告警字段抽取/意图分类 | T=0~0.2, TopP=0.5 | 要的是稳定可解析的输出 |
| 根因分析推理 | T=0.2~0.5 | 允许有限推理发散，输出仍可控 |
| 修复建议生成 | T=0.5~0.7 | 多样性有价值，但需人工审核 |
| 复现实验/单元测试 | T=0 | Mock LLM 恒定输出，测试可断言 |

**注意**：`mock-llm` 是确定性实现（保证实验可复现），它会接收这些参数但行为不变——真实模型上这两个参数的效果差异，请参考上方决策表理解。

## 2. Tokenization 从零实现（配套 tokenization_demo.py）

BPE 的直觉：**把语料里最高频的相邻字符对合并成一个新 Token，反复迭代**。实验脚本会：

1. 用一个迷你语料训练一个微型 BPE（合并 50 次）；
2. 对"小区退服告警"和"Cell outage alarm"分别 tokenize，直观看到中文切分更碎、Token 数更多 → **中文成本约为英文 1.5~2 倍**的根因；
3. 演示"相同内容不同排版"的 Token 差异（JSON 紧凑 vs 带缩进，成本差 30%+）。

## 3. Prompt Engineering 方法论：五级进阶

### 3.1 Zero-shot：直接下指令

```
你是通信网络运维专家。判断以下告警的严重级别（critical/major/minor），
输出 JSON：{"level": "...", "reason": "一句话"}
告警：eNB-1024 小区退服，影响 200 用户
```
适用：简单分类/抽取。关键：**明确输出格式**（JSON Schema 级别的约定）。

### 3.2 Few-shot：给 2~5 个示例

模型对"格式模仿"极强。告警分级这种有隐含标准（用户数、业务类型）的任务，给 3 个覆盖不同级别的示例，准确率通常显著提升。**示例要覆盖边界情况**（critical 与 major 的分界案例必须出现）。

### 3.3 CoT（Chain of Thought）：把推理过程显式化

```
请按以下步骤分析，每步给出中间结论：
1. 识别告警类型与影响面（设备/小区/用户数）
2. 检索知识库中同类历史案例
3. 结合当前网络变更单判断是否人为引起
4. 综合给出根因假设与置信度
```
原理：模型"写出"中间推理等于给下一步预测提供了更好的前文。**Trade-off：输出 Token 变多 = 成本与延迟上升**；简单任务不要滥用 CoT。

### 3.4 ReAct：推理 + 行动交错（模块 28 完整实现）

Thought → Action → Observation 循环。Prompt 里必须包含：可用工具清单及参数说明、"何时停止"的终止条件。这是 Agent 的雏形。

### 3.5 ToT（Tree of Thoughts）：多分支假设并行评估

对根因定位这类"多假设并行"问题，让模型生成 3 个根因假设，分别评估证据支持度，再选最优。实现上通常是多次采样 + 自我评估。通信场景价值高（网络故障根因天然多假设：硬件/配置/容量/外部施工）。

## 4. 运维场景 Prompt 模板库（本模块核心交付）

配套 `prompt_templates.py` 提供三个生产级模板，全部遵循五段式结构：

```
[角色设定] → [上下文注入] → [任务定义] → [输出格式约束] → [边界与兜底]
```

| 模板 | 输入 | 输出契约 | 关键设计 |
|---|---|---|---|
| 告警分析 | 告警 JSON + 设备上下文 | `{severity, impact, keywords[]}` | 明确 JSON 字段；severity 枚举封闭 |
| 根因定位 | 告警 + 最近变更单 + 历史相似案例 | `{hypotheses[], top_cause, confidence, next_steps[]}` | 强制多假设；置信度必须给理由 |
| 修复建议 | 根因结论 + 设备型号 + 权限边界 | `{actions[{step, risk, approval_required}], rollback}` | **危险操作必须标 approval_required**——这是 Agent 权限设计的 Prompt 层防线（模块 29 呼应） |

### 4.1 五段式为什么重要（面试考点）

- 角色设定：压缩分布到"运维专家"语境，术语与口径对齐；
- 上下文注入：**数据永远优于描述**——贴原始告警 JSON，不要让模型猜；
- 输出格式约束：结构化输出是 Agent 可编程的前提（`json.loads` 失败=流程中断）；
- 边界与兜底："信息不足时输出 NEED_MORE_INFO 而不是编造"——**反幻觉的最便宜手段**。

## 5. Prompt 的工程化管理（从"调咒语"到"管资产"）

1. **版本化**：模板进 Git，改 Prompt = 改代码，走评审；
2. **变量化**：上下文用 `{placeholders}` 注入，禁止字符串拼接散落各处；
3. **评估集**：每类任务维护 20~50 条标注样本，改模板后跑回归（"Prompt 回归测试"）；
4. **灰度**：新旧模板按比例分流（模块 34 的 Agent 灰度发布复用此机制）。
