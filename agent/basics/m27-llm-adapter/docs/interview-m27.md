## Q1. OpenAI、Claude、通义千问三家协议的核心差异是什么？如何设计统一适配层？

**面试官在考察什么**：是否真的接过多家 API（字段级细节骗不了人）；适配层的抽象边界是否清晰。

**标准答案**：核心差异五点：① 系统提示位置（OpenAI 在 messages 里，Claude 是顶层 system 参数）；② 工具调用结构（OpenAI 的 message.tool_calls 数组 vs Claude 的 content 块 tool_use/tool_result）；③ 认证头（Bearer vs x-api-key+版本头）；④ 流式事件结构（choices[].delta vs content_block_delta）；⑤ usage 字段名。适配层设计：内部统一消息模型（ChatMessage/ChatResponse）+ Provider 枚举分发到协议映射器 + 差异集中在 _build_request/_normalize 两处。

**加分回答**：① 指出通义/DeepSeek 等国内厂商普遍提供 OpenAI 兼容模式，生态收敛使"OpenAI 协议"成为事实标准，适配层实际只需处理 Claude 分支；② 提到 vLLM/Ollama 暴露的也是 OpenAI 协议——私有化部署零改造接入；③ 说明为什么用零 SDK 纯 HTTP 实现：依赖锁定少、协议演进可控、便于故障注入测试。

**常见误区**：只会 `import openai` 一家；把协议转换散落在业务代码；不知道 system 提示位置差异导致 Claude 调用 400。

## Q2. LLM 调用的重试、熔断、降级如何设计？各自解决什么问题？

**面试官在考察什么**：分布式系统基本功在 LLM 场景的迁移——能否区分三种机制解决的三种故障形态。

**标准答案**：重试解决**瞬时抖动**（429 限流/5xx/网络闪断），指数退避+抖动防重试风暴，4xx 不重试；熔断解决**持续性故障**（连续失败后直接短路，半开探测恢复，避免雪崩式等待）；降级解决**单厂商不可用**（主备槽位切换到备用模型/规则兜底），保证业务连续性。三者是递进关系：重试在单次调用内，熔断在槽位状态上，降级在槽位之间。

**加分回答**：① 给出降级的分级策略：一级降级换同任务小模型、二级降级换缓存/规则引擎（如告警分级回退到阈值规则）、三级降级人工兜底；② 指出幂等性前提——重试要求请求可安全重放，流式与有副作用的工具调用要小心；③ 提到 429 的 Retry-After 头应被尊重（厂商明确告知何时重试）。

**常见误区**：三层机制混为一谈；对所有错误码无差别重试；降级后不告警（静默降级导致质量劣化无人知晓）。

## Q3. 流式输出（SSE）的实现有哪些坑？如何让上层无感知？

**面试官在考察什么**：真实工程细节——流式是用户体验的关键，坑位清单能验证实战。

**标准答案**：坑位：① 中间层缓冲（nginx 默认 proxy_buffering、系统代理）导致假流式——需要 `X-Accel-Buffering: no` 或直连；② usage 只在最后一个 chunk（需 stream_options.include_usage）；③ 工具调用的 arguments 是分片 JSON 需拼接；④ 客户端断连后服务端应取消生成（省 Token）。无感知设计：适配层暴露增量回调 + 聚合后照常返回完整 ChatResponse，传输层变化不改变编程模型。

**加分回答**：① 提到 SSE vs WebSocket 的选型（SSE 单向推送足够且过代理友好）；② 首 Token 延迟（TTFT）是流式的核心指标，与模型/Prompt 长度相关——优化手段是 Prompt 精简与 KV Cache 复用；③ 前端打字机效果的背压：消费慢时暂停读取，避免内存堆积。

**常见误区**：不知道 usage 在最后一个 chunk；把流式当成纯 UI 问题忽略网关缓冲；流式异常中断没有"已收到部分内容"的降级输出。

## Q4. API Key 的安全管理有哪些要点？密钥泄露的应急流程是什么？

**面试官在考察什么**：安全意识——LLM 应用最常见的真实安全事故就是 Key 泄露刷量。

**标准答案**：管理要点：① 只经环境变量/密钥系统注入，禁止硬编码与入库（含 git 历史扫描）；② 最小权限与独立 Key（按环境/按服务分 Key，便于吊销与归因）；③ 轮换机制（定期 + 员工离职）；④ 出口监控（厂商侧用量告警 + 自建成本大盘异常检测）；⑤ 日志脱敏（sk-***）。泄露应急：立即吊销 → 审计用量损失 → 排查泄露面（git/日志/前端）→ 换发与加固 → 复盘。

**加分回答**：① 前端绝不能持有 Key——浏览器请求必须经后端代理；② 提到网关层方案（LLM Gateway 统一持钥、按租户配额），这是企业级标准做法；③ 指出 Mock/测试环境也要用假 Key 走全链路，防止"测试代码连生产"事故。

**常见误区**：认为 .gitignore 就安全（历史提交仍在）；一个 Key 用遍所有环境；泄露后只换 Key 不查泄露面。

## Q5. 如何做 LLM 调用的成本控制？给出从计量到优化的完整链路

**面试官在考察什么**：工程化闭环能力——成本是 LLM 应用能否上生产的现实约束。

**标准答案**：四步链路：① **计量**：适配层每次调用上报 model/tokens/latency/cost（on_usage 回调 → Prometheus）；② **归因**：按调用方（哪个 Skill/功能）打标，成本分解到业务线；③ **预算**：按业务线设日/月预算，超限触发告警或自动降级到便宜模型；④ **优化**：Prompt 精简（模块 26 的 Token 实验）、缓存（相同问题 KV/语义缓存）、小模型路由、批处理 API。

**加分回答**：① 给出缓存的具体分层：精确缓存（同输入哈希）→ 语义缓存（Embedding 相似度）→ 前缀缓存（Prompt 公共前缀复用厂商侧折扣）；② 量化直觉：Prompt 占比通常 80%+，优化 Prompt 比优化生成长度收益大；③ 指出流式响应的 Token 计量坑（部分厂商不计入最后 chunk 的 usage，需补偿）。

**常见误区**：只有总额监控没有业务归因；不知道语义缓存；优化只盯着换便宜模型不改 Prompt。

## Q6. 设计一个"多模型路由"方案：按什么路由？如何验证效果？

**面试官在考察什么**：从功能到架构的综合设计，考察评估方法论（没有评估的优化都是玄学）。

**标准答案**：路由维度三层：① 按任务类型（分类/抽取→小模型；推理/生成→大模型）；② 按上下文长度（超长上下文走支持窗口大的模型）；③ 按实时性（流式交互 vs 离线批处理）。验证方法：模块 26 的标注评估集在各候选模型上跑分（准确率/格式合规率/延迟/成本四指标），构建"性价比矩阵"，路由规则写成可配置的决策表；上线后 A/B 对照，用业务指标（如告警分析采纳率）而非模型自评分收敛。

**加分回答**：① 提到 cascade（级联）策略：先小模型，置信度低再升级大模型——成本可降 50%+ 且质量接近大模型；② 指出路由的监控闭环：每次调用记录"路由原因+模型+结果质量"，定期回归路由表；③ 提到故障时的强制路由（厂商故障自动全量切备份，恢复后自动回切）。

**常见误区**：按"模型排行榜"选型不看任务；路由规则硬编码不可配置；没有 A/B 就全量切换。
