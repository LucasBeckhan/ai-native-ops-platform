# 模块 29 面试题：Skill / MCP / Harness 专题（11 道必出题）

> 每道题：**面试官在考察什么** → **标准答案** → **加分回答** → **常见误区**
> 这 11 道题是 Agent 方向高级岗位的核心区分题，全部配有本项目可运行代码作为论据。

---

## Q1. 解释 Harness、Skill、MCP 三者的定位与区别，并用一个实际场景说明协作关系

**面试官在考察什么**：架构分层意识——能否用"层次"而非"功能清单"组织三者关系；类比是否准确。

**标准答案**：Harness 是 Agent 的运行时环境（生命周期/上下文/工具调度/权限/I/O/可观测），类比操作系统；Skill 是封装好的领域能力单元（元数据+工具+工作流），类比应用；MCP 是 Agent 与外部工具/数据源的标准化协议，类比 USB-C。场景：运维用户问"eNB-1024 告警怎么回事"——Harness 的会话承接请求并匹配到 alarm-analysis Skill；Skill 的工作流经 Harness 的 ToolRouter 查告警、跑诊断（数据可能来自 MCP Server）；Harness 记录全程审计后返回报告。三者各答一问：在哪运行、会做什么、怎么够到外部。

**加分回答**：① 指出"谁使用谁"的箭头方向：Agent 运行在 Harness 中、Agent 调用 Skill、Harness 经 MCP Client 连接 MCP Server；② 给出变更频率差异（Harness 平台级低频 / Skill 按需 / MCP 动态发现）及其架构含义；③ 用本项目代码位置佐证（agent_runtime.py / skills/alarm-analysis / mcp/minimal）。

**常见误区**：把三者说成互相替代（"有了 MCP 就不需要 Skill"）；把 Harness 说成"框架库"（它是运行时容器）；没有场景只有概念。

## Q2. 为企业设计 Agent 平台的 Harness 层，需要哪些核心能力？画架构图并说明

**面试官在考察什么**：平台架构设计能力——能否从单机 Demo 跳到多用户/多 Agent/可治理的企业形态。

**标准答案**（架构分层）：① **接入层**：多渠道 I/O（Web/API/IM）、认证与租户识别；② **会话与上下文层**：会话管理器（隔离/恢复）、上下文压缩、用户偏好；③ **调度执行层**：Agent 实例池、Skill 路由器、工具路由器（本地+MCP 池化连接）、异步任务队列；④ **治理层**：权限矩阵（角色×工具级别×租户）、审批流、配额与成本管控；⑤ **可观测层**：全链路审计（决策/工具调用/Token）、指标（QPS/延迟/成功率/成本）、trace 采样；⑥ **资产层**：Skill 仓库（版本/灰度）、MCP Server 注册中心、Prompt 版本库。

**加分回答**：① 强调"工具路由器是唯一执行通道"——所有工具调用必须经它，权限与审计才不漏；② 提出 MCP Client 连接池：连接复用、健康检查、自动重连（多 Server 并存是常态）；③ 指出多租户隔离的两个维度：数据隔离（上下文/记忆按租户分库）与资源隔离（配额/限流）；④ 容量视角：Harness 无状态化（上下文外置 Redis）才能水平扩容。

**常见误区**：画成"框图套框图"没有数据流；漏掉治理层（企业级与 Demo 的本质差异）；把 LLM 网关和 Harness 混为一层。

## Q3. Skill 和 Tool 的区别是什么？什么情况下应该把一组 Tool 封装成 Skill？

**面试官在考察什么**：抽象粒度的判断力——这是日常架构决策，不是概念题。

**标准答案**：Tool 是单次操作（查一次告警），由 LLM 现场决定何时调用；Skill 是一类任务的完整流程封装（告警分析=查询+诊断+报告），工作流由领域专家预先设计，LLM 只做开放性判断。封装时机三判据：① 流程稳定可预先设计；② 有领域规则需要确定性执行（如合规基线比对必须用代码）；③ 需要跨 Agent/跨系统复用（Skill 是能力包，Tool 只是函数）。反例：探索性诊断（路径不定）保持裸 Tool 让 LLM 自由编排。

**加分回答**：① 用本项目 config-audit 佐证："规则判定用代码、叙述生成用 LLM"的混合工作流是 Skill 的典型形态——审计场景 LLM 的概率性输出是负资产；② 指出 Skill 层带来的成本优势：稳定流程不必每步都过 LLM 决策，Token 成本降一个量级；③ Skill 的 I/O 契约（输入 Schema/输出格式）是可组合性的前提。

**常见误区**："Skill 就是工具的别称"（粒度和编排权完全不同）；什么都封装成 Skill（过度设计，探索型任务被锁死）；Skill 里全用 LLM 判定（不可审计）。

## Q4. MCP 协议解决了什么问题？与直接 Function Calling 相比额外价值是什么？

**面试官在考察什么**：是否理解"标准化"的经济学——MCP 的价值是生态位而非技术位。

**标准答案**：FC 解决"模型怎么调函数"（单应用内部）；MCP 解决"能力提供方与消费方怎么解耦"：① 标准化——工具方实现一次 MCP Server，任何 MCP Host 即可接入，无需为每个平台写适配器；② 动态发现——Host 运行时 tools/list 发现能力，热插拔；③ 安全边界——能力声明 + Host 侧复核，进程/网络隔离；④ 跨语言跨机——任何语言实现，本机 stdio 或远程 HTTP。本项目对比实验证明：同一 Skill 代码零差异跑通两种模式——差异全部被 Harness 的路由器吸收，这就是协议层的价值。

**加分回答**：① 给出量化判断标准：工具提供方=消费方=同一团队同一进程 → FC 足够；一旦跨团队/跨语言/需独立部署 → MCP 的接入成本一次性摊销；② 提到 MCP 生态效应（Server 注册中心、企业内能力市场）；③ 指出 MCP 不替代 FC：Host 内部把 MCP 工具转成 FC Schema 喂给模型，两者是上下游而非竞争。

**常见误区**："MCP 比 FC 更高级所以全用 MCP"（本机单团队场景是过度设计）；认为 MCP 提升模型能力（协议不改变模型）；不知道动态发现的存在。

## Q5. MCP Server 的 Tools、Resources、Prompts 三种能力有什么区别？分别适合什么场景？

**面试官在考察什么**：协议细节掌握度 + 语义设计品味（选错能力类型是真实开发中的高频错误）。

**标准答案**：Tools 是模型**主动调用**的函数，有副作用、每次调用消耗 Token、参数由模型生成——适合"动作"（查询、执行、下发）。Resources 是 Host **拉取**的只读数据源，不消耗模型决策、可缓存——适合"背景知识"（阈值表、处置手册、配置文件）。Prompts 是 Server 预置的**提示模板**，参数化生成 messages——适合把领域话术标准化（告警分析模板）。口诀：要"做"用 Tool，要"看"用 Resource，要"说得好"用 Prompt。

**加分回答**：① 用本项目 teleops-mcp-server 举例：query_alarms 是 Tool，sla-thresholds 是 Resource，alarm-analysis 模板是 Prompt——同一 Server 三种能力协同（Skill 先读 Resource 拿阈值，再调 Tool 查 KPI，Prompt 保证话术一致）；② 指出误用的两个典型：把静态知识塞进 Tool（每次白白消耗一次模型调用）、把动作包装成 Resource（只读语义被破坏）；③ 提到 Resource 订阅（subscribe）机制：数据变化主动推送（高级形态）。

**常见误区**：三种能力混为一谈；不知道 Resources 是拉取型（与 Tools 的推送调用相反）；忽略 Prompts 能力的存在。

## Q6. 如何设计 Skill 的发现与路由机制？几十个 Skill 时如何高效选择？

**面试官在考察什么**：从 3 个 Skill 到 300 个的架构演进思考——检索、成本、准确率的三角。

**标准答案**（三级路由）：① **向量初筛**：Skill 描述+触发词样本预 Embedding 入库，用户问题检索 top-5（毫秒级、廉价）；② **规则加分**：触发词/正则/用户角色匹配度加权重排；③ **LLM 终裁**：top-5 的名称+描述+一两个边界示例给小模型选一个或 none——只多一次小调用，兜住语义理解与"都不匹配"的情况。配套：Skill 数量>100 时按域分组（告警域/配置域/安全域），先路由到域再域内选择。

**加分回答**：① 指出评估闭环：路由正确率需要标注集（问题→应命中 Skill）回归，错误路由的代价分析（错 Skill 执行失败后降级到通用 ReAct）；② 冷启动策略：新 Skill 上线先用强触发词保准召，观察日志再优化；③ 缓存：同一用户会话内的重复意图直接复用上次路由结果。

**常见误区**：全部靠 LLM 选（延迟+成本双杀）；全部靠关键词（语义盲区）；没有"都不匹配"的兜底路径。

## Q7. Harness 如何保证 Agent 不执行危险操作？设计一个权限控制方案

**面试官在考察什么**：安全设计题——能否给出"分层防御"而非单点拦截；审批流的边界设计。

**标准答案**（四道防线，见本项目 permission.py 实测）：① **声明分级**：工具注册时声明级别（read/write/dangerous），写操作与危险操作明确标注；② **矩阵裁决**：角色×级别 → allow/deny/require_approval，**工具调用必须经路由器**（唯一通道保证无旁路）；③ **人工审批**：require_approval 挂起进审批流，批准只对本会话生效；deny 不可被审批推翻（硬边界）；④ **审计留痕**：允许与拒绝都记录（谁、何时、什么工具、什么裁决），支持事后回溯与攻击面分析。外加：参数值域校验（模块 28）、敏感操作二次确认的用户交互形态。

**加分回答**：① 指出"危险级不可审批"的设计理由：审批者往往在压力下批准（告警风暴时"先重启再说"），硬边界防人祸；② 运行时上下文感知：业务忙时（变更冻结窗口）自动提升审批级别；③ 与 K8s RBAC 的类比与联动：Harness 权限最终映射到工具后端的真实凭证（Agent 不持 root 凭证，按会话换取最小权限临时凭证）。

**常见误区**：只靠 Prompt 写"不要做危险操作"（提示词不是安全边界）；一层拦截就完事（旁路风险）；审批永久生效；拒绝不留痕。

## Q8. MCP 协议的安全性如何保证？Server 被恶意替换如何检测？

**面试官在考察什么**：供应链安全视角——这是 2024-2025 年 MCP 生态爆火后的真实新威胁面。

**标准答案**：四层防护：① **接入认证**：远程 Server 走 mTLS/Token（企业内 Registry 统一签发身份）；② **能力声明复核**：Host 对 Server 声明的工具做最小权限复核（声明了写操作但业务只要读 → 拒绝或降级）；③ **替换检测**：首次连接记录 serverInfo+工具 Schema 哈希指纹，后续连接指纹不符即告警阻断（防"同名工具不同行为"）；④ **运行时隔离**：Server 以最小权限容器运行（无网络出口的只读 Server、写操作 Server 走堡垒代理），爆炸半径控制。

**加分回答**：① 指出攻击场景具体化：第三方"天气查询" Server 被替换后返回内容携带 Prompt 注入，诱导 Agent 把上下文中的 API Key 发往外部——所以工具结果要标记 untrusted 且外发类工具必须审批；② 企业治理：内部 MCP Registry（签名+漏洞扫描+版本锁定），禁止私接外部 Server；③ 审计联动：每次 tools/list 的指纹变化进入审计事件流。

**常见误区**：认为"内网就安全"；只做传输加密不做能力复核；不知道工具结果也是攻击面。

## Q9. 如何设计 Skill 的版本管理与热更新机制？

**面试官在考察什么**：运维成熟度——Skill 是平台资产，资产管理能力是平台团队的日常。

**标准答案**：① **版本语义**：skill.json 带 semver 版本；主版本=I/O 契约破坏性变更，次版本=功能新增，修订号=修复；② **存储与分发**：Skill 仓库（Git）→ CI 校验（Schema 校验+评估集回归）→ 制品库（带签名的版本化包）→ 运行时拉取；③ **热更新**：运行时监听版本事件（文件 mtime/Registry webhook），加载新版本到新实例，**在途请求继续用旧版本**，新请求灰度切换（按流量比例/按租户），指标正常后全量，异常即回滚；④ **兼容性**：同一时间允许 N-1/N 两个版本并存（灰度期），旧版本的数据契约由适配层转换。

**加分回答**：① 指出热更新的真正难点是**状态迁移**：执行中的 Skill 实例持有会话事实/中间状态，版本切换要定义状态兼容或等待排空；② 评估集门禁：新版 Skill 必须跑通标注回归集（成功率不低于旧版 -ε）才允许进入灰度；③ 回滚演练：Skill 回滚应该是零代码操作（Registry 切指针）。

**常见误区**：版本号只是摆设没有契约意识；热更新=改文件即生效（在途请求被撕裂）；没有灰度直接全量。

## Q10. 对比 MCP 与传统 REST API 集成的优劣，什么场景 MCP 优势最明显？

**面试官在考察什么**：技术选型的经济学——不贬低 REST（它是伟大协议），讲清 MCP 的增量价值。

**标准答案**：REST 的问题不是"能不能调"而是"谁来适配"：每个工具的鉴权/参数/错误语义各自为政，Agent 平台要为每个 API 写专属适配器（N×M 问题）。MCP 的增量：① 统一发现（tools/list 自描述）——新工具零适配接入；② 统一语义（Tools/Resources/Prompts 三分）——Host 可以做通用治理（权限/审计/限流）；③ 面向 LLM 的设计（描述为模型优化、Schema 约束参数）——REST 的文档是给人看的。MCP 优势最明显的场景：**Agent 平台需要接入大量异构、跨团队、持续增减的内部工具**（企业运维平台/IDE 生态）；反之，单一固定后端对接，REST+薄适配层更简单。

**加分回答**：① 指出 MCP 底层也是 JSON-RPC over HTTP/stdio——它不是替代 HTTP 而是在其上约定语义；② 成本模型：接入工具数 N 越大、变更越频繁，MCP 摊销越快；N≤5 且稳定时 REST 适配器更省；③ 提到"网关混合态"：存量 REST 用协议适配器转成 MCP Server（一次性包装，存量资产复用）。

**常见误区**："MCP 更新所以更好"（论据无效）；忽视 MCP 的接入成本；认为 MCP 只能连 HTTP 服务（stdio 进程也是一等公民）。

## Q11. 多 Agent 场景中，Harness 如何管理多个 Agent 的上下文隔离与信息共享？

**面试官在考察什么**：从单 Agent 到多 Agent 的治理跨越——模块 32 的铺垫，也是 Harness 职责的深水区。

**标准答案**：隔离维度：① **上下文隔离**：每个 Agent 实例独立会话/记忆（ContextManager 按 session 隔离），防止 A 的中间推理污染 B；② **权限隔离**：每个 Agent 按职能授予工具白名单（监控 Agent 只有 read，修复 Agent 才有 write）；③ **资源隔离**：Token 预算/并发限额按 Agent 实例配额。共享维度：① **显式消息传递**：Agent 间通过结构化消息（任务书/结果报告）交换信息，而不是共享原始上下文——共享"结论"而非"过程"；② **共享工作区**：受控的公共事实板（谁写入、谁可见有 ACL）；③ **Harness 仲裁**：跨 Agent 的工具调用仍走统一 ToolRouter（审计完整、权限统一裁决）。

**加分回答**：① 用"监控→诊断→工单"三 Agent 链说明：监控 Agent 传递给诊断的是"结构化事件单"而不是对话历史——信息按需最小化，既省 Token 又防泄露；② 指出共享记忆的风险：一个 Agent 的幻觉经共享板放大为"群体共识"——共享内容需标记来源与置信度；③ 提到 Harness 的实例调度：Agent 也是资源（可暂停/恢复/销毁），长任务的 Agent 要支持状态持久化后重建。

**常见误区**：让所有 Agent 共享一个大上下文（成本爆炸+互相污染）；Agent 间点对点私连绕过 Harness（审计断链）；权限对所有 Agent 一刀切。
